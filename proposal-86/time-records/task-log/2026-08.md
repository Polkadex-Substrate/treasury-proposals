- Root cause identified:execute\_withdrawalscallsgenerate\_payloadwhich readsOutgoingNoncefrom storage and usescurrent + 1as the next slot, then unconditionally writes toOutgoingMessages\[network\]\[nonce\]— no check if that slot was already occupied
- The governance extrinsicupdate\_outgoing\_nonceaccepted any nonce value with no lower-bound validation, meaning governance could roll the counter backwards, causing the nextexecute\_withdrawalsto collide with an already-written slot
- When a slot is overwritten, any validator signatures already collected inSignedOutgoingMessagesfor the old message become permanently useless —add\_signaturesilently drops signatures whereself.message != incoming\_message, so the new message can never reach threshold and the tokens burned for both withdrawals are lost
- Fix 1: Addedensure!(!OutgoingMessages::contains\_key(network, payload.nonce), OutgoingMessageSlotOccupied)inexecute\_withdrawals— hard guard, refuses to overwrite regardless of nonce counter state
- Fix 2: Added monotonic nonce guard inupdate\_outgoing\_nonce: reads currentOutgoingNonce, rejects any new value below it withOutgoingNonceBelowFinalized— prevents the counter rollback that triggers the overwrite
- Two new error variants added to the THEA pallet: OutgoingMessageSlotOccupiedandOutgoingNonceBelowFinalized
- 3 regression testswritten and passing:
- Sequential messages get distinct nonces, no slot overwritten
- update\_outgoing\_noncerejects backwards values, accepts equal or higher
- execute\_withdrawalsrefuses to overwrite an occupied slot even when the counter is artificially reset via direct storage write
